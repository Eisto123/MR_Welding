# Evaluation Logging Implementation Specification

## Project: Vision-Based MR Object-Aligned Welding Training

## 1. Purpose

This document describes the evaluation logging system that needs to be added to the Unity project.

The paper evaluation will focus on the complete MR registration pipeline running on Meta Quest 3S:

> YOLO + Depth + SRT3D + Unity MR Registration

We will not evaluate YOLO as an isolated object detector. Instead, the goal is to measure whether the combined pipeline can support:

1. Automatic initialization and convergence.
2. Accurate registration between the virtual workpiece and the physical workpiece.
3. Real-time runtime performance on Meta Quest 3S, especially comparing continuous tracking with the pose-lock strategy.

The implementation should generate CSV logs that can be used directly for paper analysis.

---

# 2. Evaluation Sections to Support

The code should support logging for the following paper sections:

```text
5.2 Initialization and Convergence
5.3 Registration Accuracy
5.5 Runtime Performance and Pose-Lock Optimization
```

The logging system should not focus on YOLO mAP, precision, or recall. YOLO confidence and bounding box can still be logged as part of the pipeline state, but they are not the main evaluation target.

---

# 3. Required CSV Output Files

The implementation should generate three CSV files:

```text
TrialSummaryLog.csv
RegistrationAccuracyLog.csv
RuntimeFrameLog.csv
```

Recommended output folder:

```text
Application.persistentDataPath/EvaluationLogs/
```

Each test session can create a timestamped subfolder, for example:

```text
Application.persistentDataPath/EvaluationLogs/2026-06-03_1530/
```

# 4. Common Logging Concepts

## 4.1 Trial ID

Each evaluation trial should have a unique `trial_id`.

Example:

```text
Butt_001
Butt_002
TShape_001
TShape_002
```

A trial starts when the user begins an evaluation run and ends when one of the following happens:

1. The system successfully reaches pose lock.
2. The system fails to initialize after timeout.
3. The user manually stops the trial.

## 4.2 Object Types

Use consistent object type names:

```text
ButtShape
TShape
```

## 4.3 System States

Use the following enum or string values for system state:

```text
Idle
Detection
DepthInitialization
SRT3DInitialization
SRT3DTracking
PoseLock
Welding
Recalibration
Failed
```

## 4.4 Evaluation Modes

For runtime comparison, support at least two modes:

```text
ContinuousTracking
PoseLock
```

Explanation:

* `ContinuousTracking`: SRT3D remains active during welding.
* `PoseLock`: SRT3D is paused after stable convergence, and the virtual workpiece transform is fixed in Unity world space during welding.

`ContinuousTracking` or `PoseLock`.

### Timing fields

All time fields should use seconds since trial start, or absolute Unity time. Be consistent.

Recommended:

```text

```

Then calculate relative durations.


Trial start, trial end, and total duration.

```text

```

Time when YOLO first detects the correct object, and duration from trial start to that detection.

# 6. CSV 2: RegistrationAccuracyLog.csv

## 6.1 Purpose

This file supports paper section:

```text
5.3 Registration Accuracy
```

The goal is to compare:

```text
YOLO + Depth only
vs
YOLO + Depth + SRT3D
```

This is the most important accuracy comparison in the evaluation.

YOLO + Depth only represents the coarse initial pose.
YOLO + Depth + SRT3D represents the refined pose after tracking convergence.

## 6.2 Required Methods

Use the following values for the `method` field:

```text
YOLO_Depth_Only
YOLO_Depth_SRT3D
```

## 6.3 Recommended Measurement Method

Use physical reference points on the workpiece only for evaluation.

Examples:

```text
weld_start_point
weld_end_point
corner_1
corner_2
t_joint_center
edge_midpoint
```

Important:

> These physical reference points must not be used by the tracking algorithm. They are only for measuring alignment error.

For each reference point:

1. Record the physical point location in image pixel coordinates.
2. Project the corresponding virtual reference point into the camera image.
3. Calculate pixel error.
4. Optionally estimate millimeter error using depth and camera intrinsics.

Approximate conversion:

```text
estimated_error_mm = pixel_error * depth_m / focal_length_px * 1000
```

## 6.4 Required Fields

```text
trial_id
object_type
method
reference_point_id
frame_id
timestamp

physical_point_px_x
physical_point_px_y
virtual_point_px_x
virtual_point_px_y

pixel_error
depth_at_point
estimated_error_mm

view_angle
distance

pose_position_x
pose_position_y
pose_position_z
pose_rotation_x
pose_rotation_y
pose_rotation_z
pose_rotation_w
```

## 6.5 Field Meaning

```text
trial_id
```

Links this row to the corresponding trial.

```text
object_type
```

`ButtShape` or `TShape`.

```text
method
```

Either:

```text
YOLO_Depth_Only
YOLO_Depth_SRT3D
```

```text
reference_point_id
```

Identifier of the measured reference point.

Example:

```text
weld_start
weld_end
corner_left
corner_right
t_joint_center
```

```text
physical_point_px_x
physical_point_px_y
```

Pixel coordinate of the real physical reference point in the camera image.

This can be entered manually through a debug UI, selected by clicking/tapping on the camera image, or recorded from an evaluation overlay.

```text
virtual_point_px_x
virtual_point_px_y
```

Pixel coordinate of the corresponding virtual reference point after projecting the Unity world point into camera image space.

```text
pixel_error
```

2D pixel distance between the physical point and virtual point.

Formula:

```text
pixel_error = sqrt((physical_x - virtual_x)^2 + (physical_y - virtual_y)^2)
```

```text
depth_at_point
```

Depth value at or near the reference point.

```text
estimated_error_mm
```

Approximate real-world alignment error in millimeters.

```text
view_angle
distance
```

Optional test condition information.

Examples:

```text
front
30deg
60deg
0.7m
```

```text
pose_position_x/y/z
pose_rotation_x/y/z/w
```

The pose used by the current method when measuring this reference point.

# 8. Recommended Evaluation Logger Architecture

Create a Unity C# class:

```csharp
EvaluationLogger
```

Recommended responsibilities:

```text
- Create timestamped log folder.
- Create CSV files with headers.
- Start and stop trials.
- Log trial summary.
- Log registration accuracy rows.
- Log runtime frame rows.
- Flush data safely to disk.
```

## 8.1 Suggested Public Methods

```csharp
StartTrial(string trialId, string objectType, string testCondition, string mode)

RecordFirstYoloDetection(float confidence, Rect bbox)

RecordDepthInitialization(bool success, float depthValue, Vector3 initialPosition, Vector3 initialEulerRotation)

RecordSRT3DInitializationStart()

RecordSRT3DValidPose(float confidence, Vector3 position, Quaternion rotation)

RecordPoseLock(Vector3 finalPosition, Quaternion finalRotation)

EndTrial(bool success, string failureReason)

LogRegistrationError(
    string trialId,
    string objectType,
    string method,
    string referencePointId,
    int frameId,
    Vector2 physicalPointPx,
    Vector2 virtualPointPx,
    float depthAtPoint,
    float estimatedErrorMm,
    string viewAngle,
    string distance,
    Vector3 posePosition,
    Quaternion poseRotation
)

LogRuntimeFrame(RuntimeFrameData data)
```

## 8.2 Suggested Data Struct

```csharp
public struct RuntimeFrameData
{
    public string trialId;
    public int frameId;
    public float timestamp;
    public string mode;
    public string systemState;

    public float fps;
    public float frameTimeMs;

    public float yoloInferenceMs;
    public float depthQueryMs;
    public float srt3dUpdateMs;
    public float poseConversionMs;
    public float marchingCubesUpdateMs;

    public bool srt3dActive;
    public bool yoloActive;
    public bool marchingCubesActive;
    public bool poseLocked;

    public float srt3dConfidence;
    public bool trackingLost;

    public int weldBeadVertices;
    public int weldBeadTriangles;
    public int generatedWeldPoints;
}
```

## 8.3 Runtime Logging Frequency

To reduce overhead, runtime logging does not need to write every frame.

Recommended options:

```text
Option A: log every frame during short 30-second runtime tests.
Option B: log every 5 frames during longer tests.
Option C: store values in memory and write to CSV at the end of the trial.
```

Preferred:

```text
Store in memory during test, write to disk when trial ends.
```

This avoids file I/O affecting runtime performance.

# 9. Evaluation Test Procedure

## 9.1 Initialization and Convergence Test

For each object type:

```text
ButtShape: at least 5 trials, preferably 10
TShape: at least 5 trials, preferably 10
```

Each trial:

1. Place physical workpiece in the test area.
2. Start trial.
3. Run YOLO detection.
4. Run depth-based initial pose estimation.
5. Initialize SRT3D.
6. Wait until tracking confidence exceeds threshold.
7. Lock pose.
8. End trial as success.

If timeout occurs, end trial as failure.

Recommended timeout:

```text
10 seconds or 15 seconds
```

## 9.2 Registration Accuracy Test

For each successful trial:

1. Save the initial pose from YOLO + Depth only.
2. Save the refined pose from YOLO + Depth + SRT3D.
3. For each physical reference point, compare it with the projected virtual reference point.
4. Log one row per reference point and method.

Recommended number of reference points:

```text
At least 3 per workpiece
Preferably 4 to 6 per workpiece
```

Recommended methods:

```text
YOLO_Depth_Only
YOLO_Depth_SRT3D
```

## 9.3 Runtime Performance and Pose-Lock Test

Test two modes:

```text
ContinuousTracking
PoseLock
```

For each mode:

1. Initialize the system.
2. Start welding interaction.
3. Generate weld bead using Marching Cubes for a fixed duration.
4. Log runtime frame data.

Recommended duration:

```text
30 seconds per mode
```

Recommended comparison:

```text
ContinuousTracking + MarchingCubes active
PoseLock + MarchingCubes active
```

This directly tests whether pausing SRT3D after pose convergence improves runtime performance during welding.

# 10. Important Notes

## 10.1 Do Not Over-Measure YOLO

The paper does not evaluate YOLO as a standalone detector. Do not spend time implementing mAP, precision, recall, or full detection benchmark tools.

Only log YOLO information that is useful for pipeline initialization:

```text
first_yolo_detection_time
first_yolo_confidence
first_yolo_bbox
yolo_inference_ms
```

## 10.2 Reference Points Are Only for Evaluation

If physical reference markers or colored dots are used for registration accuracy measurement, they must not be used by YOLO, SRT3D, or any tracking algorithm.

The paper needs to be able to state:

> Reference points were used only for measuring registration error and were not used by the tracking pipeline.

## 10.3 Pose Lock Is an Optimization, Not a Tracking Limitation

The framework supports continuous SRT3D tracking.
Pose lock is an application-specific optimization for welding training because the physical workpiece is expected to remain stationary during welding.

The runtime evaluation should show the benefit of pose lock.

## 10.4 Use Consistent Units

Use consistent units across logs:

```text
time: seconds or milliseconds, clearly indicated in field name
position: Unity world units, preferably meters
rotation: quaternion for final pose
error: pixels and estimated millimeters
```

## 10.5 Avoid Runtime Distortion

CSV writing can affect performance. For runtime tests, store log rows in memory and write to disk after the trial ends.
